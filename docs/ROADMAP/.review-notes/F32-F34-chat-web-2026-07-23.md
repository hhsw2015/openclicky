## Issues

### Issue 1 — Content envelope wrapper is missing on F32 and F34 (CRITICAL)

`OpenClickyChatBusTools.execute` returns the raw response dict `{ok:true, message_id, delivered_to}` (`OpenClickyChatBusTools.swift:135-140, 169`). `OpenClickyWebBridgeTools.execute` does the same (`OpenClickyWebBridgeTools.swift:95-100, 120-128, 145-151`). The bridge's `executeSensorTool` puts this dict verbatim into `result.content` at `OpenClickyExternalControlBridge.swift:2555-2563`.

Every other bridge tool family wraps its dict in `{type:"text", text:"<json string>"}` before returning — see `OpenClickyConnectorBridgeTools.swift:476-479`, `OpenClickyOpenCLIBridgeTools.swift:222-225`, `OpenClickyOpenDiaBridgeTools.swift:221-224`, `OpenClickyAdapterAuthoringBridgeTools.swift:386-389`, `OpenClickyPageBridgeTools.swift:362-366`, `OpenClickyCaptureAuthoringBridgeTools.swift:378-382`, and even the sensor prefix at `:3212-3216`. The MCP `tools/call` result contract expects `content: [ContentBlock]` where a text block is `{type:"text", text:string}`.

Concrete symptom: an MCP client hitting `/mcp/sensor` for `chat_send` receives `result.content = [{ok:true, message_id:"...", delivered_to:0}]` — the block has no `type` field and no `text` field, so it fails MCP content-block schema validation. Same story for `web_search` and `web_fetch_url`.

Fix: wrap the return value inside `handleSend`, `handleSubscribe`, `handleSearch`, `handleFetch`, and the two `failEnvelope`/`errorEnvelope` paths through `sensorTextEnvelope` (or a local `textEnvelope`) before returning, mirroring `OpenClickyPageBridgeTools.swift:362-366`. Alternatively adjust `executeSensorTool` to detect a bare payload dict and wrap it, but per-family wrapping is what every other family already does.

### Issue 2 — F34 envelope uses `error` key while Everywhere uses `message` (MEDIUM)

Everywhere's `WebSearchTool.Error` helper returns `{ok:false, code:"WEB_SEARCH_ERROR", message}` (`WebSearchTool.cs:94`). Openclicky's `failEnvelope` returns `{ok:false, code, error}` (`OpenClickyWebBridgeTools.swift:145-151`) — same key rename in the F32 `AdapterAuthoring`/`Page`/`Capture` families but F32 chat itself uses `message` (`OpenClickyChatBusTools.swift:174-180`). This is an internal inconsistency: same repo pins to Everywhere via `message` for chat_bus but breaks the pin for web_*. Standardise on `message` for both to match Everywhere byte-shape, or document the intentional divergence.

### Issue 3 — `schema_version` missing on F32/F34 envelopes (LOW)

Landing report §"Contract alignment table" claims "All new tools include `schema_version: '1'`". F33/F35/F36 do add it (`OpenClickyAdapterAuthoringBridgeTools.swift:394`, `OpenClickyPageBridgeTools.swift:370`, `OpenClickyCaptureAuthoringBridgeTools.swift:386`). F32 chat_send returns `{ok:true, message_id, delivered_to}` — no `schema_version` (`OpenClickyChatBusTools.swift:135-140`). F32 chat_subscribe returns `{ok:true, messages}` — no `schema_version` (`OpenClickyChatBusTools.swift:169`). F34 web_search returns `{ok:true, count, results}` — no `schema_version` (`OpenClickyWebBridgeTools.swift:95-99`). F34 web_fetch_url same (`OpenClickyWebBridgeTools.swift:120-128`). Report claim vs code do not match. Add `"schema_version": "1"` or amend report.

### Issue 4 — `chat_subscribe` cursor-advance drops messages under filter rotation (MEDIUM)

`OpenClickyChatBus.subscribe` advances the persistent subscriber's `sinceTs` to `matched.last.ts` (`OpenClickyChatBus.swift:166-168`). If the same subscription_id is later called with a stricter filter, older messages that would have matched the new filter but had `ts <= cursor` are skipped — even if they were never delivered to the caller before. This differs from Everywhere's model (extension replays from `since_msg_id`, cursor is caller-supplied per-call).

Two options: (a) advance the cursor to `max(matched.ts)` only over messages that would still match under the *previous* filter, or (b) never persist filter fields — treat cursor as filter-agnostic. Current behaviour is documented in-code as "repeated subscribe calls can rotate filters" (`OpenClickyChatBus.swift:170-173`) which is misleading: rotation loses history.

### Issue 5 — `OpenClickyChatBus` `.metadata: MetadataValue` cannot round-trip nested containers (LOW)

`MetadataValue` (`CaptureTypes.swift:2655-2682`) only encodes `string / number / bool / null`. `decodeMetadata` at `OpenClickyChatBusTools.swift:189-203` silently drops nested arrays/dicts. Everywhere passes metadata as opaque `JsonObject?` (`ChatBusTools.cs:79`) — full JSON tree survives. This is documented at `OpenClickyChatBusTools.swift:198-200` but the wire schema description at `:63-64` says "flat metadata bag (values must be JSON scalars)" while the callers on the Everywhere side may pass arbitrary objects and will not be told they were dropped. Consider adding a warning to the response when nested keys are stripped.

### Issue 6 — `OpenClickyWebFetchClient` sends the redacted URL upstream (LOW)

At `OpenClickyWebFetchClient.swift:88-89`, the request URL is replaced with the credential-redacted form before the fetch. If the target legitimately requires `?token=...` for authentication, the redacted URL will 401. The inline comment (`:82-87`) says "upstream servers should not be receiving those tokens in the first place through this free-lane tool" — this is defensible, but the docstring on `web_fetch_url` (`OpenClickyWebBridgeTools.swift:47-49`) claims "credentials are redacted from the outbound URL before the request" without mentioning the trade-off. Either allow a `preserve_credentials: bool` opt-in or document the failure mode explicitly.

### Issue 7 — `web_fetch_url` bypasses the `data` cap when converting to string (LOW)

`OpenClickyWebFetchClient.fetch` caps `data.prefix(maxBytes)` for the cap purposes (`OpenClickyWebFetchClient.swift:124-130`), but `bytes_read` is set from `data.count` (`:168`) — the full response size before capping. Semantics are ambiguous: the wire response reports `bytes_read=<uncapped>` while `text` was built from the capped slice. Report `bytes_read = capped.count` to avoid misleading callers about how many bytes they actually got.

### Issue 8 — F32 tools/list description text drift from Everywhere (LOW / cosmetic)

Everywhere's `chat_send` description: `"Send a message to chat. client_msg_id enables idempotency; extension rejects duplicates IDEMPOTENCY_CONFLICT if content differs."` (`ChatBusTools.cs:69-70`). Openclicky's `chat_send` description: `"Publish one message onto the OpenClicky chat bus. Any subscriber whose filter accepts (kind, from) receives it. Messages TTL out after 5 minutes; the bus holds at most 200 messages ..."` (`OpenClickyChatBusTools.swift:39-42`). Descriptions do not byte-match. Given the semantic divergence (in-process vs extension-proxied), byte-matching is impossible — but flag as intentional divergence in the landing report.

## Verdict

**F32 chat_bus**: ships 2/6 of Everywhere's tools with intentional semantic divergence (in-process bus vs extension proxy). Wire contract is well-documented but Issue 1 (missing text envelope wrapper) breaks MCP schema compliance and must be fixed before an MCP client can consume these tools. Issue 3 (schema_version claim vs code) needs a report or code amendment.

**F34 web_***: byte-shape aligned on `web_search` output; `web_fetch_url` intentionally diverges. Issue 1 (envelope wrapper) blocks MCP compliance. Issue 2 (message vs error key rename) breaks byte-shape parity with Everywhere.

**Bridge wire**: 4/4 F32+F34 names wired through `sensorToolNamesBase`, `sensorToolDomainsBase`, descriptor concat, and dispatch switch. Domain gating for `.chat` and `.web` works correctly via `activate_domain`. No prefix collision with `advisor_web_search`. PASS modulo the payload-wrap defect in Issue 1.
