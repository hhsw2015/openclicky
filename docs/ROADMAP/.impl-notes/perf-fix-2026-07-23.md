## HIGH #1 — F29 / F30 unbounded 2s respawn loop

### Before
- `OpenClickyConnectorSubprocess.swift:320-327` (old) — `handleTermination`
  always slept 2s then unconditionally called `start()`. A persistent
  `EPERM` / bad-config crash produced a 2s spin loop pinned at 100% of
  the auto-restart cadence forever.
- `OpenClickyOpenCLISubprocess.swift:287-292` (old) — same shape.

### After
- `OpenClickyConnectorSubprocess.swift` lines added around the old
  block; now:
  - `private var restartAttempts: Int = 0` state,
  - `private static let maxRestartAttempts = 10`,
  - `static let subprocessFailedNotification =
    Notification.Name("com.jkneen.openclicky.connector.subprocess.failed")`,
  - `handleTermination` computes
    `delay = min(pow(2, attempt), 60)` seconds,
  - resets counter to 0 on a successful health probe path in `start()`,
  - after 10 attempts posts the failure notification and stops the
    respawn chain.
- `OpenClickyOpenCLISubprocess.swift` — identical shape with
  `com.jkneen.openclicky.opencli.subprocess.failed` name.

Grep sanity: `restartAttempts` now appears 8 times per file (declaration,
class-level state, reset in `start()` success path, reset at top of
`stop()`, and 4 uses in `handleTermination` incl. the `attempt` capture).

Test scenario:
1. Break `boot.js` by throwing at top-of-file.
2. Toggle the Connector / OpenCLI subprocess on in Settings.
3. Verify HeyClickyLog / Console: crashes retry at ~2, 4, 8, 16, 32,
   60, 60, ... second intervals rather than 2s flat.
4. After 10 crashes, a `NotificationCenter` post on
   `subprocessFailedNotification` fires; last-status-message reports
   auto-restart disabled.
5. Fix `boot.js`, hit the Settings "Test" button to explicitly `start()`
   — `restartAttempts` resets to 0.

## MEDIUM #2 — `HeyClickyChromeBridgeServer.eventLog` unbounded

### Before
`cursor-buddy/HeyClickyChromeBridgeServer.swift:42` — `eventLog` grew
forever, one entry per Chrome-bridge event over the app's whole
lifetime.

### After
- Added `private let eventLogMaxEntries = 500` next to the declaration.
- `recordEvent` now trims after append:
  ```swift
  eventLog.append(ev)
  if eventLog.count > eventLogMaxEntries {
      eventLog.removeFirst(eventLog.count - eventLogMaxEntries)
  }
  ```
- Guarded implicitly by `@MainActor` on the class (same isolation as
  every existing `eventLog` access — no new lock).

Test scenario: exercise the Chrome extension for 500+ events (e.g. open
many tabs, navigate). Verify `eventLog.count` capped at 500 and no
older events leak. `closeTabsMatching` still finds recent tabs.

## MEDIUM #3 — `OpenClickyProgressMarkerCheck.isDone` off main actor

### Before
Synchronous file read + regex on `@MainActor` inside every
`turn/completed` handler (fires per turn). Path in
`CodexAgentSession.swift` ~:2038.

### After
Signature unchanged (`static func isDone(path:marker:) -> Bool`) — call
site refactored instead, mirroring the guidance in the audit.

`CodexAgentSession.swift` ~:2038 area (now ~:2045-2072):
- Wrapped the marker check in `Task { ... await Task.detached { ... }.value }`
- File read + regex now execute off `@MainActor`
- `NotificationCenter.default.post` moves inside the async block, still
  fires the same `.heyClickyRequestAutoContinueReplay` notification with
  the same `userInfo` shape when the marker is absent.
- `HeyClickyLog.log` also moved inside the async block, so the log
  event contains the actual `marker_found` result (unchanged semantics).

`CompanionManager+HeyClicky.swift:459` — `hasInterruptedInFlightTurn`
call site is a synchronous predicate feeding a guard-return inside
`NotificationCenter` observer bodies. Making it async would require
restructuring the observers' control flow (the observers already
branch immediately on the predicate). Since this path fires only on
rare lifecycle events (codex crash, soft-interrupt notifications) and
not on every `turn/completed`, the hot path is now off-main; leaving
this sync path is a conscious trade-off documented here rather than
risk changing the guard-return semantics.

Grep sanity: `Task.detached` at `CodexAgentSession.swift:2044`.

Test scenario:
1. Trigger a heyclicky-free progress-driven turn.
2. Have `PROGRESS.md` on a slow file system (or a large marker sweep).
3. Confirm UI stays responsive during `turn/completed` — the
   `openclicky.f28.progress_check` log entry still fires with
   `marker_found` populated, and the auto-continue notification still
   posts iff the marker is missing.

## LOW #4 — F29 / F30 `stop()` main-actor blocking poll

### Before
Both `stop()` methods spun on `Thread.sleep(forTimeInterval: 0.05)`
for up to 3s on the caller's actor (`@MainActor` when invoked from
Settings toggles) — could stall UI for 3 seconds while waiting on
SIGTERM.

### After
Both files: `stop()` now dispatches the terminate-wait to
`DispatchQueue.global(qos: .utility).async { ... }`. The SIGKILL
fallback runs on the same background queue. `handleTermination(reason:
"stop()")` still fires synchronously so the state flip is immediate.

Grep sanity:
- `OpenClickyConnectorSubprocess.swift:268` — `DispatchQueue.global(qos: .utility).async {`
- `OpenClickyOpenCLISubprocess.swift:241` — same.

Test scenario: toggle Settings "Enable Connector" / "Enable OpenCLI"
rapidly. UI does not freeze; the Node subprocess still SIGKILLs after
3s if it fails to terminate cleanly.

## MEDIUM regression — overlays lack voice-turn hide hook

### Decision: DEFER — no existing voice-active signal to subscribe to.

Grep for existing signal candidates:
- `voiceTurnActive`, `voiceTurnStarted`, `voiceTurnEnded`,
  `isVoiceTurnActive`, `voice_turn_active` — 0 matches anywhere.
- Closest existing state is
  `BuddyDictationManager.isRecordingFromKeyboardShortcut` /
  `isRecordingFromMicrophoneButton`, which covers push-to-talk audio
  capture but not the full "voice conversation turn" lifecycle (TTS
  playback, agent response streaming, etc.) that the audit implicitly
  wants overlays hidden during.

Per task instructions ("If no existing signal: skip this fix, document
as follow-up. Do not invent a new signal for this pass."), this is
deferred. The overlays in question
(`OpenClickyWhiteboardOverlayWindow`, `OpenClickyLinkRectOverlayWindow`,
`OpenClickyPickElementOverlay`, `OpenClickyAnnotationBadgeOverlay`) are
all hotkey-gated, so accidental mid-conversation triggers require the
user to press a hotkey — the risk surface is small.

Follow-up work item: introduce
`Notification.Name.openClickyVoiceTurnStarted` /
`.openClickyVoiceTurnEnded` (posted by `CompanionManager` at the top
and bottom of the voice-turn state machine) and have each overlay
observe the pair and self-dismiss on start.
