# F27 codex sensor config — fix report (2026-07-23)

Fixes Wave 3 review issues from `docs/ROADMAP/.review-notes/F27-codex-sensor-config-2026-07-23.md`.
Scope constrained to the 5 files called out in the task; no other code touched.

## Fixes applied

### 1. MEDIUM — Port drift (Issue 1)

- `OpenClickyExternalControlBridge.swift`
  - Added thread-safe `activePort` static (populated when the listener
    reaches `.ready`, cleared on `stop()`).
  - Added `onPortResolved: ((UInt16) -> Void)?` per-instance callback so
    a bind-fallback ladder outcome can propagate to config writers.
- `ClickyCodexConfigTemplate.swift`
  - New `bridgePort: UInt16?` field + `effectiveBridgePort`
    (`bridgePort ?? resolveDefaultPort()`) + `bridgeBaseURL` helper.
  - Sensor block (`:181-186`) and openClickyControl block (`:163-169`)
    now interpolate `bridgeBaseURL` in place of `http://127.0.0.1:32123`.
  - HeyClicky-lane sensor block (`:300-305`) also uses `bridgeBaseURL`.
- `CodexHomeManager.swift`
  - `writeCodexConfigFromSettings()` reads
    `OpenClickyExternalControlBridgeServer.activePort ?? resolveDefaultPort()`
    and passes it as `bridgePort` on the template.
- `CompanionManager.swift`
  - `startExternalControlBridgeIfNeeded()` installs an `onPortResolved`
    handler that calls `rewriteCodexConfigIfPortChanged` on the main
    actor. Re-renders only when the current config's sensor URL does
    not already contain the freshly-bound port, so we do not thrash
    the file on every launch.

### 2. LOW #1 — startup_timeout_sec race (Issue 2)

- `ClickyCodexConfigTemplate.swift`
  - Emits `startup_timeout_sec = 10` on both `[mcp_servers.sensor]`
    blocks (general + HeyClicky lane) and `[mcp_servers.openClickyControl]`.
- `CompanionManager.swift`
  - Reordered startup: `startExternalControlBridgeIfNeeded()` now runs
    BEFORE `startRelaunchableAgentAutoResumeChecks()` (previously
    lines `2425` then `2429`) so the listener is at least submitted
    before auto-resume kicks off. The `startup_timeout_sec = 10`
    cushion covers any remaining binding delay on the bridge queue.

### 3. LOW #2 — Plaintext token on disk (Issue 3) + Issue 4 rotation

- `ClickyCodexConfigTemplate.swift`
  - Added `static let bridgeTokenEnvVarName = "OPENCLICKY_BRIDGE_TOKEN"`.
  - Both sensor blocks and the openClickyControl block now emit
    `bearer_token_env_var = "OPENCLICKY_BRIDGE_TOKEN"` instead of a
    `[mcp_servers.*.http_headers]` sub-table carrying the plaintext
    `x-openclicky-token`. The template no longer needs the token
    VALUE at render time — `sensorMCPToken` still gates emission (a
    nil/empty token means the block is dropped so codex does not
    start with a doomed 401 handshake) but the string is not written
    to disk.
- `CodexProcessManager.swift`
  - `baseEnvironment` now sets
    `environment[ClickyCodexConfigTemplate.bridgeTokenEnvVarName]`
    from `AppBundleConfiguration.externalControlBridgeToken()`,
    falling back to `OPENCLICKY_AUTOMATION_TOKEN` (matches
    `hasValidBridgeToken` acceptance in the bridge). Only sets when
    the caller has not already provided the var — respects test-time
    overrides. Because this env is snapshotted at spawn time, token
    rotation via UserDefaults/Info.plist takes effect for the NEXT
    session automatically (Issue 4 falls out of Issue 3).
- `CodexHomeManager.swift`
  - Updated comment on `sensorToken` to document that it is now
    emission-gate-only, not written to disk.

### 4. Latent — openClickyControl block missing auth (Issue 5)

- `ClickyCodexConfigTemplate.swift:163-169`
  - `[mcp_servers.openClickyControl]` now emits the same
    `startup_timeout_sec` + `bearer_token_env_var` pair as the sensor
    block. The `/mcp` route on the bridge is auth-gated
    (`OpenClickyExternalControlBridge.swift:323-329`), so prior to
    this fix any codex agent enabling `includeOpenClickyControlMCP`
    would 401 on every call. Since both blocks now use the same env-
    var indirection, alignment is by construction.

## Alignment audit

Both `[mcp_servers.sensor]` and `[mcp_servers.openClickyControl]` now
share the identical shape:

```
[mcp_servers.<name>]
url = "http://127.0.0.1:<effectivePort>/<path>"
startup_timeout_sec = 10
bearer_token_env_var = "OPENCLICKY_BRIDGE_TOKEN"
```

Codex reads `OPENCLICKY_BRIDGE_TOKEN` once from its spawn env, so a
single injection in `CodexProcessManager.baseEnvironment` covers both
blocks with no duplication. Bridge acceptance
(`OpenClickyExternalControlBridge.swift:663-684`) already handles both
`x-openclicky-token` and `Authorization: Bearer` forms — the rmcp
client sends the value as `Authorization: Bearer <token>`.
