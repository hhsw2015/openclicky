# 06. Component ↔ Profile Decoupling Audit

Scope: can Advanced Settings mix STT / TTS / dialog LLM / agent LLM freely across the 3 profiles (heyclickyFree, ski, mirage/peekyFree)?

Short answer: **STT and TTS are cleanly decoupled at the enum/UserDefaults level. Dialog LLM is decoupled per-model. Agent LLM and warm-lifecycle are coupled by accident, largely because they are wired into the profile-switch path rather than component setters.**

---

## Well Decoupled

- **STT is a bare enum keyed by UserDefaults.** `BuddyTranscriptionProviderFactory.resolveProviderSelection` (`cursor-buddy/BuddyTranscriptionProvider.swift:155-222`) switches purely on the persisted rawValue; no profile check. `mirageDeepgram` is fungible with regular `deepgram` (`:212-222`, comment: "Not bound to any specific profile: any profile can select it in Settings."). A mirage-profile user can pick native Deepgram; a heyclicky user can pick mirageDeepgram.
- **TTS is a bare `@Published` enum.** `setTTSProvider` (`cursor-buddy/CompanionManager.swift:1078-1100`) writes UserDefaults and rebinds the client; no profile lock. `.mirageCartesia` shares the `cartesiaTTSClient` singleton (`:984`) and only differs in the `tokenProvider` closure wired in `bindCartesiaTokenProviderForCurrentProvider` (`:994-1008`) — so any profile picking `mirageCartesia` gets aegis-proxy auth automatically.
- **Advanced Providers exposes the full matrix without filtering.** `advancedVoiceProviderPanel` (`OpenClickySettingsWindowManager.swift:4892-5100`) renders `OpenClickyTTSProvider.allCases` (`:4999`), the full response-voice-model catalog (`:4902-4907`), and `BuddyTranscriptionProviderFactory.providerIDsForSelectionGrid()` (`:4974-4983`) with no profile gate. This IS the advanced-mixing surface the audit asked about.
- **Dialog LLM branches on `model.provider`, not profile.** `_analyzeVoiceResponseCore` (`CompanionManager+AIResponsePipeline.swift:845`) switches on `selectedVoiceResponseModel.provider`; whichever model the user picks, that transport runs — profile is not consulted. `.peekyFree` → `analyzeMirageResponse`; `.heyclickyFree` → `HeyClickyChatToolCallClient`; `.anthropic` → `analyzeClaudeResponse`. `MiragePeekyOrchestrator` itself contains zero `activeProfile()` checks — it runs whenever the model provider is `.peekyFree`, regardless of profile.

## Coupled by Design (OK)

- **Provider tagging on `OpenClickyModelOption`** (`OpenClickyModelCatalog.swift:97`, `.peekyFree` at `:14`, `.heyclickyFree` at `:9`). Each backend needs its own transport (Mirage proxy strips `mirage/`, HeyClicky proxy carries OAuth). The enum is the switch key; per-provider silo is unavoidable at the request layer. Cross-profile mixing still works because profile ≠ provider.
- **Realtime speech models own their own audio.** `setSelectedModel` (`CompanionManager.swift:2117-2153`) forces `.openAIRealtime` TTS when a speech model is chosen. This is correct: speech-to-speech models cannot be paired with an external TTS.
- **`heyclicky-free-*` special-cases inside `CodexAgentSession`** (`:794, 869, 1088-1467`) — HeyClicky agent turns must go through the HeyClicky proxy, not the user's Codex key. Justified.
- **`switchingIntoHeyClicky` / `switchingAwayFromHeyClicky` subsystem toggle** in `applyProfile` (`CompanionManager+Profiles.swift:29-40`) — HeyClicky WebSocket, plan poller, token refresh loops must lifecycle with the profile because they carry auth state. Documented rationale in the comment at `:22-27`.
- **`analyzeMirageResponse` as its own code path** (`AIResponsePipeline.swift:2521`) rather than a case in `analyzeClaudeResponse`. Reasoning: it does 5-intent orchestration + dock-shim + heartbeat, which the paid Anthropic path doesn't. Living beside the switch (not inside a shared function) is fine because it is triggered by the `.peekyFree` model tag alone, not the profile.

## Coupled by Accident (Should Fix)

1. **`applyProfile` writes `agentModelID` into the shared `clickyCodexModel` key** (`OpenClickyProfile.swift:178-180`; `CompanionManager+Profiles.swift:90-92`). Peeky's `agentModelID = "mirage/claude-opus-5"` (`OpenClickyProfile.swift:145`) lands in the key that `CodexAgentSession` (`:401`) and `CodexHomeManager` (`:40`) read as the Codex agent model. `CodexAgentSession` only special-cases `heyclicky-free-*` (`:794`); it has no `mirage/` handling — so a Peeky profile switch pollutes Codex agent state with an ID the Codex lane cannot execute. Peeky's own agent runner reads a *different* key (`openClickyMirageAgentModel` via `ClaudeAgentRunner.claudeAgentModelDefaultsKey`, `ClaudeAgentRunner.swift:83`). Two overlapping "agent model" keys, and `applyProfile` writes the wrong one for Peeky. Already flagged in `04-regression-risk.md#R3`.

2. **Warm-hook is bound to profile switch, not component activation.** `switchingIntoMirage` (`CompanionManager+Profiles.swift:31, 42-71`) warms `MirageDeepgramClient`, `MirageCartesiaClient`, and `OpenClickyIntentClassifier` only when the profile flips into mirage. `setVoiceTranscriptionProvider` (`CompanionManager.swift:2602-2604`) and `setTTSProvider` (`:1078`) do NOT warm the mirage clients when a non-mirage-profile user picks `mirageDeepgram` / `mirageCartesia` in Advanced Settings. Result: the first PTT after that switch pays 1-2 s cold-start that the profile path takes pains to hide. `start()` at `:2693` also gates warm on `activeProfile().id == "mirage"` for the same reason. Warm should key off component selection, not profile ID.

3. **Dialog/agent split is Peeky-only.** `PeekyFreePanelView.agentModelGroup` (`PeekyFreePanelView.swift:256-279`) exposes an independent agent-model picker backed by `ClaudeAgentRunner.claudeAgentModelDefaultsKey`. `HeyClickyFreePanelView` has one `modelGroup` (`:158-177`) plus an Assist Agent toggle (`:237`); `SKIModePanelView.body` (`OpenClickySettingsWindowManager.swift:4012-4024`) exposes voice-skill / whisper / hands-free / hotkeys but no dialog or agent model picker at all. Cross-profile parity gap: HeyClicky and SKI users cannot choose an agent tier separate from dialog even though the underlying storage (`clickyCodexModel` vs `openClickyMirageAgentModel`) already supports it.

4. **Heyclicky promo/quota UI hides on non-heyclicky profile.** `heyClickyBasicPromo` in `OpenClickySettingsWindowManager.swift:1452-1526` returns `EmptyView` when `activeProfile().id != "heyclicky_free"`. But HeyClicky sign-in mints tokens for STT and Realtime that a Peeky or SKI user can legitimately consume; the state panel disappears exactly when it would be useful for mix-and-match. Same coupling anti-pattern as R2 — profile check where a component check belongs.

5. **SKI Mode short-circuit is profile-gated, not component-gated.** `_analyzeVoiceResponseCore` (`AIResponsePipeline.swift:747`) hard-checks `activeProfile().id == "ski_mode"` before routing to `OpenClickyFileBridge`. A user on `local` profile with `whisperLocal` STT + a local workspace loaded gets the normal pipeline instead of the file bridge. The bridge is really "there is a workspace and the user opted into CLI relay," which is orthogonal to profile.

## Missing Abstractions

- **No `WarmupLifecycle` bus.** Each of `MirageDeepgramClient`, `MirageCartesiaClient`, `OpenAIRealtimeSpeechClient`, `CodexVoiceSession`, HeyClicky Realtime hook has its own `warm()` called from a mix of `applyProfile`, `setTTSProvider`, `setSelectedModel`, `setVoiceTranscriptionProvider`, and `start()`. No single point of truth for "component X is now active; warm its transport." The R2 leak above is a direct consequence.
- **No `AgentBackend` protocol.** Codex process (`CodexProcessManager`), HeyClicky Codex-proxy (`CodexAgentSession :794-1467`), and Peeky's Claude Code (`ClaudeAgentRunner`) each own their own model-selection storage and each get switched on by string-prefix inside `CodexAgentSession`. A protocol with a single `selectedModel` key would eliminate the R1 stale-write hazard.
- **No component-level UI in the profile-specific panels.** Peeky and HeyClicky panels re-implement filtered pickers scoped to their own catalog subset (`mirageModelIDs` in `PeekyFreePanelView.swift:129`, `heyClickyModelIDs` in `HeyClickyFreePanelView.swift:152`). The `AdvancedProvidersPanelView` shows the union but is documented as "cross-profile". A middle tier — "components used by this profile, with a Change... affordance that jumps to Advanced" — is missing; users currently have to know that Advanced Providers exists.

## Over-abstracted

- **`OpenClickyProfile.agentModelID` is functionally redundant.** Only `.peekyFree` and `.heyclickyFree` set it, and in both cases the same value could be derived from the response model's provider (Peeky → `mirage/claude-opus-5`; HeyClicky → `heyclicky-free`). Storing it as a first-class profile field forces every consumer to keep two model IDs in lockstep (see `ClaudeAgentRunner.swift:104` comment "kept in lockstep so Settings and Runner agree even if the two ever disagree on which is authoritative").
- **Two writers to `clickyCodexModel`.** `OpenClickyProfileCatalog.apply` (`OpenClickyProfile.swift:179`) writes it, and `applyProfile` in `CompanionManager+Profiles.swift:91` also writes it. Same key, same value, two sites — one path is enough.
- **Duplicated "is this profile active" checks.** Both `applyProfile` (`:28`) and `_analyzeVoiceResponseCore` (`:747`) and `start()` (`:2693`) read `UserDefaults.standard.string(forKey: OpenClickyProfileCatalog.activeProfileDefaultsKey)` (or the `activeProfile()` wrapper). A `didChangeActiveProfile` notification with `previous`/`next` payload would centralize the diff and let each component subscribe once.

## TL;DR

STT and TTS: mix-and-match is fully supported end-to-end. Dialog LLM: mix-and-match works via the Advanced panel; the pipeline branches on model.provider not profile. Agent LLM and warm-hooks: NOT decoupled — both are wired into `applyProfile` rather than into the setters, so a user changing an individual component through Advanced Settings gets a partial upgrade (correct client selected, cold transport, wrong `clickyCodexModel` residue).
